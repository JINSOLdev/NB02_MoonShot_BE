## 프로젝트 소개
Moonshot은 팀 협업과 프로젝트 관리를 돕는 서비스 입니다. </br>
사용자는 프로젝트 생성, 팀원 초대, 업무 관리, 댓글을 통한 소통 등 다양한 협업 기능을 이용할 수 있습니다. </br>
또한 실시간에 가까운 업데이트와 직관적인 UI를 통해 효율적인 협업 환경을 경험할 수 있습니다. </br>

## 담당 기능
### 1. Member (프로젝트 멤버 관리)
- 프로젝트 멤버 초대/추가/제외
- 초대 수락/거부 처리
- 초대 상태(pending, accepted, rejected) 기반 멤버 관리 로직 구현
- 프로젝트 생성자만 멤버 제외 가능하도록 권한 체크 로직 적용

### 2. Comment (할 일 댓글 관리)
- 할 일에 대한 댓글 등록/수정/삭제 기능 구현

### Deploy (배포 및 인프라 관리)
- CI/CD : GitHub Actions를 활용해서 빌드 (main 브랜치에 push 시 워크 플로우 자동 실행)
- Vercel을 활용한 프론트엔드 서비스 배포 및 관리
- Render를 활용한 백엔드 서비스 배포 및 관리

## 구현 중 겪은 문제 & 해결

### 1. 프로젝트 생성자 보호 및 요청-대상 식별자 분리

문제 </br>
- 프로젝트 생성자가 실수로 본인을 프로젝트에서 제외할 수 있는 비즈니스 로직 버그 발견
- 기존 API는 단일 userId 파라미터만을 사용하여 요청자와 삭제 대상을 명확히 구분하지 못했고, 이로 인해 생성자 본인에 대한 예외 처리가 정상적으로 동작하지 않음

고민 </br>
- 비즈니스 규칙상 생성자는 시스템의 근간이므로 스스로를 파괴할 수 없다는 원칙을 코드 레벨에서 어떻게 강제할 것인가
- API 설계 단계에서부터 요청 주체(Actor)와 조작 대상(Target)을 명확히 분리하지 않으면 나중에 권한 관리 시스템이 복잡해질수록 유지보수가 불가능해질 것이라 생각함

해결 </br>
- API 및 서비스 로직에서 식별자를 requestUserId와 targetUserId로 분리
- 이후 다중 가드 로직을 도입함
- targetUserId === project.creatorId: 생성자 제거 시도 시 403 에러 반환
- requestUserId === targetUserId: 자기 자신 제거 시도 차단
- checkProjectAdmin: 요청자가 실제 관리 권한이 있는지 선행 검증

결과 </br>
- 생성자 보호라는 핵심 비즈니스 규칙을 보장하게 됨
- 식별자 분리를 통해 코드의 가독성과 유지보수성 향상시킴
- 트랜잭션 도입으로 인해 데이터 불일치 가능성을 차단하는 성과를 거둠

### 2. N:M 관계 테이블(Project_members)의 역할 재정립 및 자동화

문제 </br>
- 초기 설계된 Project_members 테이블이 실제로는 활용되지 않고, Invitations 테이블에만 데이터가 쌓이는 현상 발생
- 이로 인해 프로젝트 생성 시 생성자가 멤버 목록에서 누락되거나, 초대를 수락해도 실제 멤버로 등록되지 않는 등 데이터 모델과 비즈니스 로직 간의 괴리 발생

고민 </br>
- 초대 내역(History)과 현재 멤버 상태(State)를 어떻게 분리하고 동기화할 것인가

해결 </br>
- 테이블의 역할을 명확히 재정의하고 로직을 자동화함
- Project_members: 실제 프로젝트에 참여 중인 현재 멤버 관리 (Source of Truth)
- Invitations: 프로젝트 참여를 위한 초대 프로세스 기록
- 프로젝트 생성 시 creatorId를 Project_members에 자동 삽입하고, 초대 수락 시 트랜잭션을 통해 Invitations 상태 업데이트와 Project_members 추가를 동시에 수행하도록 리팩토링 진행

결과 </br>
- 데이터 구조와 비즈니스 로직의 일관성이 확보됨
- 초대 상태와 참여 상태가 분리됨으로써 시스템의 확장성이 높아짐
- 트랜잭션 처리를 통해 어떤 상황에서도 멤버 정보가 누락되지 않는 시스템 구축

### 3. FE 사용자 경험 개선을 위한 API 확장 및 클라이언트 최적화

문제 </br>
- 백엔드에서 초대 수락 API는 완성되었으나 프론트엔드(FE) UI에서 이를 테스트하거나 사용할 수 있는 경로가 없음
- 사용자가 본인에게 온 초대 목록을 확인할 수 있는 API가 부재하여, Postman 없이는 기능을 검증할 수 없는 '반쪽짜리' 구현 상태였음

고민 </br>
- 명세서에 있는 내용만 구현할 것인가, 실제 사용자의 흐름(User Flow)을 고려하여 완성도를 높일 것인가? 

해결 </br>
- API 확장: 유저 본인의 초대 목록을 조회할 수 있는 GET /invitations/me 엔드포인트를 신규 개발
- 클라이언트 최적화: next/headers 참조 오류를 방지하기 위해 클라이언트 전용 Axios 인스턴스를 별도로 구축, revalidatePath를 활용해 멤버 목록을 새로고침 없이 즉시 갱신하도록 구현
- UI 통합: 초대함 패널 컴포넌트를 제작하여 실제 서비스 환경과 동일한 수락/거절 플로우 완성

결과 </br>
- 단순 API 구현을 넘어 실제 사용자 시나리오를 완성함으로써 프로젝트의 완성도를 높임
- 기술적으로는 Next.js의 하이브리드 렌더링 환경에서 발생할 수 있는 참조 오류 해결
- 서버 액션과 클라이언트 상태 동기화에 대한 이해 기회

## 회고
이번 프로젝트에서는 FE/BE 연동 과정에서 발생한 이슈와 트러블슈팅 내용을 날짜별로 공유하며 협업을 진행했다.</br>
이를 통해 내가 담당한 기능뿐 아니라 프로젝트 전반의 흐름과 다른 파트에서 발생하는 문제까지 함께 이해할 수 있었고, “이 기능을 내가 구현했다면 어떻게 했을까?”라는 관점에서 한 단계 더 깊이 고민할 수 있었다. 

또한 코드 머지 전 필수 리뷰어 지정과 PR 템플릿을 활용해 모든 변경 사항이 코드 리뷰를 거치도록 했고, ESLint, Prettier, Husky, lint-staged를 도입해 코드 스타일 차이로 인한 불필요한 충돌을 줄였다.
그 결과 리뷰 과정이 스타일 논의보다 로직과 설계 중심으로 진행될 수 있었고, 팀 프로젝트임에도 코드의 일관성과 안정성을 유지할 수 있었다.

다만 전반적인 협업은 원활했지만, 팀원 간 실시간 음성 소통이 부족했던 점은 아쉬움으로 남았다. </br>
개발 과정에서 생각이나 고민을 말로 풀어내는 빈도가 줄어들다 보니, 일부 이슈는 문서나 메시지로만 공유되어 논의가 충분히 확장되지 못한 부분도 있었다. 그래서 다음 프로젝트에서는 데일리 스크럼에서 음성으로 주요 진행 상황과 이슈를 공유하는 것을 기본으로 하여
의사소통의 밀도를 높이고, 문제를 더 이른 시점에 발견할 수 있도록 개선하고자 한다.

또한 FE/BE 연동 테스트를 개발 막바지가 아닌 기능 단위 완성 시점마다 소규모로 진행해 수정 사항이 한 시점에 몰리는 현상을 줄이고, 일정 리스크를 낮추는 방식으로 발전시키고 싶다.

마지막으로 코드 품질과 성능 개선 효과를 보다 명확히 확인하기 위해 린트 에러 수, API 응답 시간, 테스트 커버리지와 같은 정량적인 지표를 측정·기록하는 체계를 도입해
지속적으로 개선해 나가는 개발 방식을 실천해보고자 한다.
